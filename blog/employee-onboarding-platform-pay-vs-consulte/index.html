What a scoped onboarding pilot includes (identity, apps, checklist — not “HRIS replace”)

An employee onboarding platform, done honestly, is not a new HRIS and not a black box that “grants everyone access.” It is a scoped joiner path from identity through apps to a Day-1 checklist — with humans still owning manager approvals and security exceptions.

Typical surfaces a Zion pilot can touch (one at a time, with a definition of done):

  • Identity / IdP joiner — a named path from HRIS hire event (or agreed intake) into the identity provider for one cohort, with a human gate on incomplete or high-risk records.
  • Apps access — provision or request a defined app set for that cohort. AI does not grant access alone by default — manager and IT gates stay in the loop. Adjacent IT framing: managed IT services.
  • Day-1 checklist — a visible, owned checklist (equipment, training, manager tasks) so “Day-1 ready” is an operating signal, not a vibe.
  • HRIS / IT handoff — stage or write the agreed fields when access and field mapping are known — with an acceptance owner. This is a handoff, not an HRIS replacement.
  • Exception paths — clear escalation when automation should stop (privileged roles, regulated entities, contractor vs employee splits, a security veto).

What it is not: a promise to “cut time-to-productivity by X days,” an HRIS rip-and-replace, unsupervised access grants, or a multi-country works-council program hidden inside a single SKU. If a vendor leads with invented NPS, days-saved math, and logos, treat that as marketing — not a pilot SOW. Zion’s lane is operational clarity first; see employee onboarding platform. Mid-market onboarding stalls when leadership buys “AI onboarding” as a vibe while the bottleneck is ownership: who owns the hire record, who approves app access, who owns the IdP connector. Automation without those answers becomes another checklist HR ignores.

So the commercial question is not “should we automate onboarding?” It is “is the first improvement scoped enough to Pay for Starter ZG06, or do we still need Consulte / Discovery because the process map and security ownership are politically multi-owned?”

Consulte for multi-entity, works councils, or unclear security ownership

Consulte via /contact/ is the right first move when package SKUs are the wrong unit — not because you are “enterprise theater,” but because onboarding’s real blockers are political and control-shaped.

Consulte first when:

  • Multi-entity maze — several legal entities, hire types, or approval chains with no single process owner for joiner rules.
  • Works councils / labor design — employee-representation, consultation, or local labor rules that must be designed before any helper touches joiner data or automated messaging.
  • Unclear security ownership — nobody can grant IdP or HRIS staging rights, privileged-role rules are contested, or IT / security will block a $2,500 pilot without RACI. Adjacent IT conversation: managed IT services.
  • Privacy and access politics — who may see a joiner record, who approves privileged apps, and who owns the exception after hours are unresolved; automation would amplify the fight.
  • Custom SOW needed — larger than Starter, spanning multiple countries or regulated evidence requirements before automation touches identity payloads.

Consulte is not “the expensive version of Discovery.” It is the path when you need stakeholder design, control language, and a SOW shape before money hits a pilot.
